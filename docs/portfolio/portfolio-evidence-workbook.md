## 1. 기록 규칙

이 문서는 기존 근거를 확인하고 다음 검증을 설계하기 위한 작업표다. 회사 자료에서 확보한 6사례의 사실·흐름·집계·한계는 [사내 프로젝트 근거 요약](company-evidence-snapshot.md)에 보관한다. 집에서 원본 저장소에 접근할 수 없어도 해당 요약을 사용해 개편한다. 문서 기록 확인·코드 읽기·직접 파일 집계를 구별하며 운영 서비스나 모델을 재실행한 상태는 아니다.

상태는 `기존 서술 / 원본 확인 / 측정 예정 / 미측정 / 공개 제외`로 관리한다. 원본 확인 이후에도 자기 사용·팀 내부 사용·외부 사용을 구별한다. 회사 자료와 원고의 원문·개인정보·비밀 rubric은 공개 문서에 넣지 않고 비식별 요약과 공개 가능한 증거 위치만 기록한다.

## 2. 증거 한 건의 기록 양식

```text
증거 ID / 프로젝트 / 기록자:
확인하려는 주장:
관찰 기간 / 측정일:
대상 사용자와 작업 / 자기 사용·내부·외부 구분:
표본 수 / 분모 / 제외 조건:
기존 방식 또는 baseline:
변경한 경험 / 직접 맡은 범위:
측정 방법 / 시작·종료 조건 / 실행 환경:
결과 / 실패 / 예외:
원본 증거 위치 / 공개 가능한 요약:
해석 한계 / 미확인 사항:
다음 판단 / 판단을 바꿀 기준:
상태 / 연결할 포트폴리오 문장:
```

비교 조건이 다르면 단순한 전후 개선률로 쓰지 않는다. 과거 수치를 회수할 수 없으면 추정 근거를 밝히거나 정성 사례로 작성한다.

## 3. 대표 사례의 최소 검증 설계

### AI Writer: 실제 장문 집필 한 건에서 시작

실제 사용하는 원고 하나를 선택하고 장 수·글자 수·관찰 기간을 기록한다. 실제 작업 세션을 누적해 검토하되 ‘10시간 사용’ 자체를 성공 기준으로 삼지 않는다. 합성 테스트와 실제 원고 사용을 구별하고, 자기 사용 결과를 외부 작가 수요로 일반화하지 않는다.

| 질문 | 기록할 값 | 해석할 때 주의할 점 |
| --- | --- | --- |
| 필요한 설정을 찾는 데 도움이 되는가? | 검색 과제, 기존 방식과 제품 방식의 소요 시간, 정답/실패, 확인한 근거 | 과제 난이도와 순서에 따른 학습 효과 기록 |
| 기억 제안이 유용한가? | 검토한 후보 수, 승인·수정 승인·거절·판단 보류 수, 이유 | 승인율 = 승인 수 / 검토 완료 수. 미검토 후보를 성공이나 실패로 처리하지 않음 |
| 생성 제안이 도움이 되는가? | 제안 수, 검토 수, 채택 수, 수정 유형과 수정 시간 | 기억 승인과 원고 생성 채택은 다른 지표 |
| 일관성 문제를 잡는가? | 사람이 확인한 결함, 도구 지적, 오탐·누락, 원문 확인 결과 | 비교 가능한 사람 기준이 없으면 정확도·재현율을 주장하지 않음 |
| 검토 부담을 늘리지는 않는가? | 검토 시간, retrieve_more 횟수와 이유, 작업 중단·재시도 | Gate 일치율은 같은 평가 단위·판단 기준을 가진 표본에서만 계산 |

첫 파일럿 후 반복되는 마찰 한 가지를 골라 유지·수정·보류를 결정한다. 시간 비교를 할 수 없더라도 실제 실패 사례와 판단 이유를 남긴다. 외부 작가 인터뷰는 별도 후속 작업이며, 모집·연락은 이 계획의 실행만으로 자동 수행하지 않는다.

### 영상: 품질과 제작 부담을 따로 확인

먼저 실제 요청자와 운영자의 기존 흐름을 인터뷰 또는 기존 기록으로 확인한다. 비교 가능한 brief에 대해 요청 확정→생성 시작 시간, 운영자 개입 수, 재생성 수, 사람이 검토한 최종 사용 가능 여부를 기록한다. GPU 비용은 측정 가능할 때만 추가한다.

기존 실험의 음악 경계·화면 정보량·화면 한글·인물 목소리·연속성 이슈를 품질 체크의 참고로 사용한다. 현재는 사용자 설명으로 레퍼런스 기반 연속성·목소리 일관성을 일정 수준 구현했으며, 남은 과제는 모델별 결과 품질임을 반영한다. 동일 유형·길이·실행 환경을 함께 기록한다. 생성 성공률과 최종 사용 승인율은 별도로 계산한다. 품질 기준을 통과하지 못하면 생산성 개선만으로 완성 제품이라고 결론 내리지 않는다.

### Assessment: 실제로 접근 가능한 자료부터 확인

실제 spec과 대응 rubric을 함께 확보할 수 있는 과제부터 작은 파일럿을 한다. 3~5쌍에서 규칙과 평가 방법을 점검한 뒤 접근 가능한 경우 10~20쌍으로 확대한다. 공개 take-home의 spec만 확보되면 비공개 rubric과의 불일치는 평가할 수 없다. 만들어 붙인 rubric은 합성 데이터로 명시한다.

사람이 검토한 mismatch 기준을 먼저 만들고 도구 finding과 대조한다. finding 중 실제 불일치로 확인한 비율, 오탐 사유, 사람의 검토 시간, 도구 실행 후 검토 시간을 기록한다. 전체 정답 목록이 없으면 누락률이나 recall을 주장하지 않는다. deterministic/mock 경로의 결과와 live LLM 결과를 분리한다.

## 4. 기존 실무 사례를 확인할 질문

### 제품의 발견·첫 사용·재사용·복구 질문

사용 시간과 인터뷰 수만 쌓는 대신 아래 질문에 대한 관찰을 기록한다. 아직 수행하지 않은 인터뷰·피벗·기능 축소를 과거의 제품 개발 이야기처럼 쓰지 않는다.

| 질문 | 최소 기록 | 판단에 사용하는 방법 |
| --- | --- | --- |
| 왜 이 문제를 골랐는가? | 실제 작업에서 겪은 문제, 빈도·비용, 기존 대안, 자기 경험인지 타인의 경험인지 | 중요하지만 관찰되지 않은 수요는 가설로 유지 |
| 첫 10분 안에 무슨 가치를 얻는가? | 첫 가치 행동의 정의, 시도 수, 성공 수, 소요 시간, 막힌 지점 | 예: 실제 설정을 출처와 함께 찾아 집필에 활용. 가입·화면 진입만으로 활성화 성공을 정의하지 않음 |
| 다시 사용하는가? | 돌아올 작업 기회가 있었던 사용자 수, 재사용 수·간격·이유, 미사용 이유 | 자기 사용도 기록하되 외부 retention으로 표현하지 않음. 단발성 업무에는 반복 작업 완료·다음 배치 사용을 적용 |
| AI가 틀렸을 때 복구할 수 있는가? | 잘못된 제안의 발견, 거절·수정·되돌리기·재검색 과정, 복구 시간, 이후 영향 | 승인 단계의 유무와 실제 복구 가능성을 구분 |
| 무엇을 안 만들었는가? | 고려한 기능, 보류 이유, 가장 싼 대안, 다시 검토할 조건 | 기술적 난이도에 의한 유예와 사용자 가치에 의한 우선순위 결정을 구별 |
| 피드백으로 무엇이 바뀌었는가? | 관찰/피드백 ID → 결정 → 변경 → 같은 작업 재관찰 | 변경 전후 기록이 없으면 ‘피드백 기반 개선’이라고 쓰지 않음 |
| 품질·지연·비용 중 무엇을 선택했는가? | 같은 작업에서의 실패 비용, 대기 시간, 비용, 선택한 기준 | ‘품질 5% vs 지연 절반’은 가상 선택지. 실제 비교 근거가 있을 때만 수치 사용 |

GTM·가격·시장은 외부 제공이나 사업화가 목표인 사례에서 조사한다. 내부 도구라면 도입 주체·배포 방식·교육·유지 비용을 확인한다. 모든 프로젝트에 매출·결제·retention KPI를 일괄 요구하지 않는다. 외부 사업화 의도가 미확정이면 먼저 제품 사용자를 확인한다.

### 실무 자료 회수

아래 질문은 최초 수집 설계다. 이미 확인한 내용은 근거 요약의 AST-01·NLP-01·OPS-01·STF-01을 사용하고 다시 회수를 기다리지 않는다. 추가 확인이 필요한 항목은 최종 배포·사용량·시간 산식·사후 절감 근거·적용 후 서비스 수준이다. 기존 자료의 조건을 확인한 수치와 새로 측정해야 하는 지표를 구별한다.

## 5. 공개 요약의 짧은 템플릿

제품·업무 사례:

```text
대상과 문제: 누가 어떤 작업에서 어려움을 겪었나?
제품 판단: 어떤 경험을 선택했고, 어떤 범위를 제외했나?
사용 흐름: 기존 방식 → 바꾼 방식
현재 결과: 구현 / 실제 사용 / 효과 측정 중 어디까지 확인했나?
한계와 다음 판단: 아직 모르는 것과 다음에 확인할 근거
상세 근거: 기술 구조·테스트·측정 자료 링크
```

연구 사례:

```text
가설 → 비교 실험과 조건 → 관찰 결과 → 유지/전환/중단 판단
미구현 후속 방향은 결과와 분리해 가설로 표기
```

숫자가 없어도 대상·의사결정·실패·검증 상태를 정확히 설명한 요약부터 공개할 수 있다. 미측정 항목이 있다는 이유로 기존의 확실한 결과까지 숨길 필요는 없다.

# 포트폴리오 개편 핸드오프

## 목표와 이어가기 원칙

AI Product Builder 관점에서 **사용자 문제→제품 판단→업무/UX→구현→검증→다음 결정**을 보여주는 포트폴리오로 개편한다. 기술 깊이와 실패 기록은 보존하되 기술 구조·테스트 수를 대표 성과처럼 앞세우지 않는다.

사용자는 집에서 회사 저장소에 접근할 수 없다. 회사 자료를 다시 열지 않고 아래 근거 요약으로 문구 개편을 진행한다. 부족한 사실은 사용자 확인 항목으로 남기고, 답변이 없는 주장만 미확인으로 유지한다. 전체 작업을 확인 대기로 멈추지 않는다.

## 공개 문구 원칙 — 사용자 정정 반영

2026-10-01 사용자가 PROJECTS에 답변 대기 사항을 ‘미측정/미확인’으로 노출한 것을 지적했다. 앞선 개편에서 자료를 확보하지 못한 상태를 실제 측정·활용의 부재처럼 표현하고 내부 검토 메모를 공개 포트폴리오에 넣은 것은 잘못이다.

- 사용자에게 확인해야 할 질문·산식·공개 범위·직접 기여는 `owner-confirmations.md`와 근거표에만 둔다. 공개 PROJECTS·README·웹에 ‘사용자 확인 필요’, ‘근거 확인 중’, ‘이번에 확인 못함’ 같은 작성 과정의 메모를 넣지 않는다.
- 답변 전에는 확인된 문제·판단·작업 흐름·구현 결과로 완결된 소개를 작성한다. 사용자 답변 전에는 성과를 생략한다. 이번 답변으로 인력 3명·600만 원 절감과 월간보고 2일→반나절 미만 성과를 반영했다. 월 10시간으로 환산하지 않았다.
- 자료가 없다는 사실만으로 ‘미측정’, ‘실사용 없음’, ‘인터뷰 없음’을 단정하지 않는다. 질문 목록도 실제 수행 여부를 묻는 상태이지 부재를 판정한 결과가 아니다.
- 실제로 확인된 PoC·개발 상태, 합성 자료 검증, 미구현 기능, 실험 실패와 기술 제약은 프로젝트의 범위로 설명한다. 미확인 성과를 확정된 결과로 되돌려 쓰지 않는다.
- 이번 수정은 PROJECTS 두 언어뿐 아니라 README 두 언어·홈·실무·케이스 페이지에도 함께 반영했다. 질문은 삭제하지 않으며 답변을 받으면 관련 항목별로 갱신한다. 수정 후 공개 7파일에 내부 확인 대기 표현이 없는지 검사했고 로컬 링크·한영 검사, `git diff --check`, Chromium 12개 조합을 다시 통과했다. 기존 세 커밋은 push하지 않았고 후속 수정 커밋을 추가한다.

## 완료한 작업과 아직 하지 않은 작업

- 회사 자료를 읽어 영상·에셋·NLP·사내 자동화·인력 분석·RAG의 개편용 요약을 확보했다. 인력 보고서는 8페이지를 직접 판독했고, 에셋은 로컬 파일에서 집계했다.

- README 두 언어와 홈 소개를 사용자 문제·경험·검증 상태 중심으로 개편했다. 홈의 Memory/Harness 노출을 줄이고 인력 분석·영상·Assessment를 연결했다. NLP 비교 배수는 홈에서 내렸고 에셋 수치를 생성 인덱스로 한정했다.

- 계획·근거 문서는 `c5fc4b0`, README·홈 개편은 `077d5e7`으로 커밋했다. PROJECTS·상세·검증 결과와 이 핸드오프는 후속 커밋으로 함께 기록한다(`git log` 확인). 사용자가 필요한 만큼 커밋하면서 진행하도록 승인했다. 완료한 묶음마다 검증과 핸드오프 갱신 후 커밋한다. push는 수행하지 않는다. 재개할 때 `git status --short`를 확인하고 다른 변경을 보존한다.

## 다음 작업자가 바로 진행할 순서

1. `git status --short`와 최근 커밋, 이 문서들을 확인한다. P1의 문구 개편과 P2/P4의 근거 기반 정리는 완료했다. 회사 저장소를 다시 탐색하거나 같은 개편을 반복하지 않는다.
2. [사용자 확인 목록](owner-confirmations.md)은 **8개 확인 완료, 5개 일부 답변, 2개 미답변**이다. 미답변은 OWN-01(남은 사내 집계의 공개 범위)·OPS-03(특정 CMS/API 재사용 흐름)이며 공개 본문 전체를 막지 않는다. 공개 제외한 상세 인건비·사내 레퍼런스 구성은 재질문하지 않는다. 답변이 충분한 현재 상태와 사용 단계는 다시 확인받지 않는다.
3. 답변이 도착하면 확인 목록→근거 요약→증거표→계획 상태→본문 순으로 반영한다. 한영·Markdown·웹을 같은 묶음에서 맞춘다. 없는 성과와 사용자 수를 만들어내지 않는다.
4. P3에서 Writer는 직접 집필·dogfood 중임을 확인했다. 세부 개선 사례는 사용자 요청에 따라 Writer README 작업 때 이력으로 정리한다. 영상·RAG는 본인 테스트 위주의 개발 단계이며 실제 업무 사용 전이다. Assessment는 추가 진행이 없고 대표 노출에서 내렸다. 새로운 파일럿을 사용자 요청 없이 현재 완료 과제로 요구하지 않는다. 합성 테스트나 개발자 검토를 외부 사용자 검증으로 승격하지 않는다.
5. P5 PDF 갱신: `박요한_AI_Writer_포트폴리오.pdf`는 14쪽이며 이전의 일관성 단정과 118/315/3,075 중심 설명이 남아 있다. `박요한_경력기술서.pdf`는 18쪽이며 600만 원·10시간 절감 문구가 남아 있다. 두 PDF는 보존했고 현재 본문과 동기화되지 않았다. 기존 편집 원본/생성 경로는 이번 작업에서 확정하지 않았으므로 찾아서 재생성한다. 정적 웹을 내보낸 파일을 기존 경력기술서의 편집본으로 취급하지 않는다.
6. 확인이 부족하면 해당 성과를 미확인으로 유지한 상태에서도 PDF 문구를 본문 수준으로 정리할 수 있다. 최종 파일의 언어·페이지 구성·그림·링크를 직접 검토한다.
7. 포트폴리오 개편과 검증 정리가 끝나면 P6로 [경력기술서 저장소](https://github.com/entangelk/job_activate)의 관련 문서·산출물을 동기화한다. 요청은 이미 승인된 후속 범위이며 현재 그 저장소의 파일은 수정하지 않았다.

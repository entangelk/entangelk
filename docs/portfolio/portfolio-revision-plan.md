## 1. 이번 검토의 결론

첨부된 「AI Product Builder 포트폴리오 개편 가이드」의 핵심인 **사용자 문제와 제품 판단을 먼저 보여주고 기술 검증을 뒤에 두자**는 방향을 채택한다. 현재 자료의 강점은 구현·검증 깊이와 실패를 공개하는 태도다. 이를 유지하면서 실제 업무 변화와 사용자 행동을 읽기 쉽게 만든다.

다만 첨부 글은 수정 지침이지 프로젝트 사실을 확정하는 증거가 아니다. “영상은 가장 강한 사례”, “대표 사례는 반드시 세 개”, “작가 다섯 명이면 충분” 같은 제안은 가설로 다룬다. 대표 사례의 위치는 확인 가능한 근거에 따라 정하고, 인터뷰나 사용 시간 자체를 제품 효과로 해석하지 않는다.

이번 작업은 이 저장소의 README·프로젝트 상세·웹 포트폴리오를 위한 계획이다. 최초 검토는 공개 서술을 대조했고, 이후 회사 자료에 접근할 수 있을 때 영상·에셋·NLP·사내 자동화·RAG의 문서와 필요한 구현, 에셋 집계 파일, 인력 보고서 8페이지를 확인했다. 결과는 [사내 프로젝트 근거 요약](company-evidence-snapshot.md)에 저장했다. 서비스 재실행·운영 DB 조회·사용자 인터뷰·공개 사이트 렌더링은 수행하지 않았다. 아래 ‘기존 근거’ 표는 최초 공개 서술 대조이며, 최신 근거와 주장 한계는 근거 요약을 우선한다.

추가 평가의 **‘개발하기 위한 기획이 많고 무엇을 만들어야 하는지의 검증이 부족하다’**는 지적도 채택한다. 공개 자료만으로 사용자 발견·재사용·피드백에 따른 변경을 충분히 판단하기 어렵다. 이는 실제 역량 부재를 확정하는 근거와는 구별한다. 기술 결정을 사용자 언어로 바꾸기만 해서는 부족하며, P3에서 실제 행동과 판단의 연결을 확인해야 한다.

추가 평가에 나온 ‘작가 8명 인터뷰’, ‘수정 시간 40분→18분’, ‘자동 저장을 승인 방식으로 변경’은 설명용 가상 사례다. 이 포트폴리오의 실적으로 인용하지 않는다.

## 3. 개편 원칙과 목표 정보 구조

- 첫 요약에서 **누구의 문제 → 선택한 경험 → 현재 결과 → 남은 한계**를 읽을 수 있게 한다. ‘Why AI’는 AI를 사용한 사례에만 적용한다.
- 사용자·업무·제품 판단을 충분히 설명하되 30/30/20/20 비율이나 아홉 항목을 모든 카드에 강제하지 않는다.
- 제품 결과, 시스템 측정, 개발 과정의 기록을 구별한다. 테스트 수와 리뷰의 실패 비율만으로 검증의 품질이나 제품 효과를 입증하지 않는다.
- 수치에는 기간·대상·분모·측정 조건·증빙 위치를 붙인다. 없으면 미측정 또는 증빙 확인 대기로 표시한다.
- 생성 화면과 GIF는 구현 경험의 근거다. 사용자가 문제를 해결했다는 근거는 별도로 모은다.
- 기존 코드·연구·실패 기록은 보존한다. 요약을 줄이고 상세로 연결한다.
- 한국어·영어와 Markdown·웹의 프로젝트 상태, 수치, 주장을 함께 맞춘다.

기술 판단이 제품 판단으로 이어지는지 확인할 질문은 다음과 같다.

| 판단의 층위 | Writer의 승인 구조 예시 | 필요한 근거 |
| --- | --- | --- |
| 기술 선택 | 후보 저장, 검증, append-only 기록 | 코드·회귀 검증·복구 동작 |
| 사용자 경험 선택 | 사용자가 언제 근거를 확인하고 무엇을 승인하며 오류를 어떻게 되돌리는가 | 실제 화면·작업 흐름·사용자 관찰 |
| 제품 우선순위 | 자동 생성·설정 검색·모순 탐지 중 무엇을 먼저 제공하며 무엇을 보류하는가 | 기존 작업의 비용·수요·대안 비교 |
| 제품 검증 | 승인 단계가 오류를 줄이는 이득보다 검토 부담을 더 만들지는 않는가 | 실패·검토 시간·채택·재사용 기록 |

승인 UX가 있다는 사실만으로 사용자 검증을 완료했다고 쓰지 않는다. 반대로 기술적 안전장치라는 이유만으로 제품 판단의 가능성을 버리지도 않는다.

| 배치 | 프로젝트 | 노출 기준 |
| --- | --- | --- |
| 대표 제품 판단 사례 | AI Writer, 영상 시스템, Assessment 후보 | 최대 3개. 각자 개발 중·최종 사용 품질 미해결·PoC 상태를 붙인다. 근거가 약하면 짧게 소개하고 실무 사례에 더 많은 공간을 준다 |
| 실무 결과 | 인력 분석, 에셋 생성·검수, NLP, 사내 자동화 | 확인된 변화와 직접 맡은 일을 먼저 노출. 인력 분석은 필요에 따라 대표 사례로 승격 가능 |
| 기술 기반 | Verified RAG, Agent Memory | 검색·검증·기억 구조의 근거. 사용자 성과가 없으면 제품 성과로 포장하지 않는다 |
| 연구 아카이브 | Logo Workbench, Harness IR, HW-WFC, Q-PSA, Circle-WFC, T-WFC | 가설·관찰·판단으로 압축. 로고의 실제 업무 맥락이 확인되면 위치 재검토 |
| 보조 경력 | 네트워크 유틸리티 | 경력 페이지에 짧게 유지 |

WFC 계열은 연구 시리즈로 묶되 Q-PSA는 WFC에서 영감을 받은 별도 perturbation 실험임을 유지한다. collapse/propagation을 구현한 WFC 알고리즘으로 소개하지 않는다. 별도 R&D 페이지 추가는 분량을 정리한 뒤 필요할 때 결정한다.

**공개 문구 원칙(사용자 정정):** 사용자 확인 대기와 작성자의 근거 확보 상태는 작업 문서에서 관리한다. 공개 본문에는 확인된 업무·판단·구현 결과와 실제 프로젝트 범위를 적고, 답변 대기 성과는 생략한다. 자료를 못 찾았다는 이유로 미측정·실사용 부재를 단정하지 않는다.

## 4. 단계별 실행 계획

상태 값: `대기 / 진행 / 증빙 대기 / 완료`. 일정은 목표 작업량이며 실제 사용자 확보나 자료 접근 시간을 보장하지 않는다. P0/E01은 사내 자료 1차 확인과 요약을 완료해 진행 상태이며, 미확인 실적은 따로 남긴다. P1은 완료했다. P2/P4의 현재 근거로 가능한 본문 정리와 P5 웹 검토도 완료했다. 사용자·성과 확인, P3 실제 사용, PDF 동기화와 P6는 남아 있다.

| 페이즈 | 작업과 산출물 | 대상 파일 | 완료 기준 | 예상 작업량 |
| --- | --- | --- | --- | --- |
| P0 근거 정리 | 증거표 작성, 기존 수치 원본 확인, 최신 상태와 직접 기여 확인 | [증거 수집표](portfolio-evidence-workbook.md) | 공개할 주장은 근거와 연결되고 미확인 주장은 표시됨. 자료가 없는 항목은 다음 단계로 넘길 수 있음 | 1회 작업 + 자료 회수 |
| P1 첫인상 개편 | 프로필 소개 압축, 제품·실무·기술·연구 재배치, Assessment 한 줄 수정, 과장 표현과 단정 완화 | README.md / README.ko.md / docs/index.html / PROJECTS.md / PROJECTS.ko.md | 첫 요약에서 대상·문제·현재 상태가 읽힘. 테스트 수가 대표 성과를 대신하지 않음. 한영 주장이 일치함 | 1~2회 작업 |

의존 순서: **P0 → P1 → P2 → P5 1차 검토**, 실제 사용 자료는 P2 이후 P3에서 모으고 **P3·P4 → P5 최종 검토**로 반영한다. P3 결과를 기다리느라 사실에 근거한 문장 정리를 미루지 않는다. 자료가 없으면 현재 상태와 검증 계획을 공개하고 다음 항목을 진행한다.

**후속 작업 메모(2026-10-01 사용자 요청):** 모든 포트폴리오 개편 단계가 끝나면 [경력기술서 저장소](https://github.com/entangelk/job_activate)에 있는 자료도 업데이트한다. P5 최종 검토 이후 P6를 수행하며, 관련 문서·원본·배포 산출물의 범위는 해당 저장소를 확인해 정한다. 이 연결에는 로컬 경로 대신 GitHub 링크를 사용한다. 현재는 저장소 remote로 주소를 확인했으며 해당 저장소의 파일은 수정하지 않았다.

**집에서 이어갈 작업을 위한 메모(2026-10-01 사용자 정정 반영):** 사내 경로 목록 대신 지금 읽은 자료에서 개편에 필요한 사실·업무 흐름·제품 판단·수치 조건·실패와 한계를 추린 [근거 요약](company-evidence-snapshot.md)을 이 저장소에 남긴다. 이 요약만으로 P1·P2·P4의 문구 개편을 진행할 수 있다. 원본 코드·로그·PDF·이미지·사내 주소·인증값·개인별 자료는 반입하지 않았다. 추가 회사 자료가 필요한 것은 미확인 지표의 보강이며 본문 개편 전체의 선행 조건이 아니다. 사용자가 2026-10-01 필요한 만큼 커밋하며 핸드오프를 갱신하도록 승인했다. 완료한 묶음별로 커밋한다.

## 6. 다음 작업에서 바로 시작할 묶음

C01~C04와 B01~B04/R01의 현재 근거 기반 문구 개편은 완료했다. W01/V01/A01은 작업 흐름과 판단을 본문에 반영했고 실제 사용 증거가 남아 있다. Q01은 12개 브라우저 조합의 웹 검토를 마쳤으나 기존 PDF 동기화가 남아 있어 완료하지 않았다. 다음은 [사용자 확인 목록](owner-confirmations.md)의 답변 반영과 P3 실제 사용, PDF 갱신이다. 질문 항목 자체를 완료로 바꾸지 않는다.

인력 산정 사례를 홈의 대표 목록과 실무 페이지 앞쪽에 배치했다. 현재 확인된 연결은 문제→데이터→운영 기준→역검증이며, 사용자 답변으로 실제 채용 반영·전년 대비 3명·600만 원 절감을 추가했다. 적용 후 서비스 수준은 후속 질문이다.

현재 Writer 소개를 바꿀 때의 방향 예시:

> 장편 창작자가 이전 원고의 설정을 찾아 다음 집필에 활용하도록 만드는 글쓰기 워크스페이스입니다. 원고에서 제안된 기억은 근거를 확인하고 승인한 뒤 검색에 사용합니다. 로컬 관통 동작과 생성 화면은 확인되었으며, 실제 집필에서의 시간 절감과 일관성 개선은 현재 포트폴리오 자료로 확인되지 않았습니다.

위 방향을 본문에 반영했다. 실제 사용자와 최신 사용 기록이 확인되면 효과와 다음 판단을 보강한다.

## 7. 개편 완료 점검

- [ ] 첫 요약만 읽어도 각 사례의 사용자·문제·핵심 선택·현재 상태를 구분할 수 있다.
- [ ] 회사 프로젝트, 개인 PoC, 실서비스 적용, 연구 결과가 서로 다른 상태로 표시된다.
- [ ] 수치에 분모·조건·기간·증거가 있고, 제품 효과와 시스템 지표가 섞이지 않는다.
- [ ] 핵심 가설을 확인 사실처럼 쓰지 않고 실패와 검증 한계를 남긴다.
- [ ] 한영·Markdown·웹·배포 PDF 간 주장과 링크를 검토한다.
- [ ] 대표 사례별 다음 판단과 그 판단을 바꿀 증거를 기록한다.

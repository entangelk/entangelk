## 읽는 방법과 공개 범위

원본 코드·로그·이미지·PDF를 복사하지 않고 문서와 필요한 구현을 읽어 업무 흐름·판단·집계 결과만 새로 요약했다. 사내 경로·주소·계정·인증값·고객/직원 식별정보·개별 상담 실적·광고 원문은 포함하지 않았다. 사내 저장소를 연결할 공개 GitHub 주소는 확인하지 않았으므로 임의로 링크를 만들지 않는다. 기존에 공개한 성과도 원본 확인 범위를 넘어 해석하지 않는다.

- **파일 집계 확인**: 현재 디스크의 로컬 자료에서 직접 계산했다. 운영 DB의 최신 집계가 아니다.
- **구현 확인**: 해당 화면/처리 코드가 있다. 실제 사용량과 효과를 뜻하지 않는다.
- **기록 확인**: README·가이드·작업 로그·실험 보고서의 해당 서술을 확인했다. 이번에 재실행한 결과가 아니다.
- **미확인**: 조사한 자료에서 근거를 확보하지 못했다. 효과가 없다는 판정도 아니다.

문서상의 요구·예정 기능과 현재 구현, 실험 성공과 사용자가 승인한 품질을 구별한다. 이 요약을 공개 본문의 문장으로 옮길 때에는 아래 ‘바로 쓸 수 있는 방향’과 ‘제외할 주장’을 함께 적용한다.

## VID-01 — 영상: 자연어 요청에서 승인·생성·구간 수정까지

**확인 자료**: 제작 요구사항 정리(v4, 2026-09-09), 현재 상태 인계 문서(2026-10-01), 같은 날 작업 로그와 기능 데모 보고서. 최신 기능 데모를 직접 시청한 것은 아니다.

**사용자와 일**: 업무 측 대표·직원이 자연어로 광고 의도를 입력해 짧은 SNS용 영상을 만드는 것이 요구사항이다. 실제 사용자 인터뷰나 기존 제작 시간은 이번 자료에서 확보하지 못했다.

**확인한 제품 흐름과 선택**:

1. 광고 의도를 입력하고 분석된 시나리오를 확인한다.
2. 필요한 참조 이미지를 생성하거나 제공하고 사람이 검수한다. 이미지가 필요한 흐름에서는 시나리오 확인을 먼저 하도록 정했다.
3. 검토된 입력을 영상 생성과 완성본 조립에 사용한다. 사람이 생성 그래프를 자유롭게 조립하는 경험 대신 의도·시나리오·참조를 다루게 한다.
4. 완성본의 일부 범위에 수정 지시를 주면 새 revision을 만든다. 원본은 보존한다.

모든 경로에서 사람이 반드시 brief를 승인한다고 단순화하지 않는다. 요구사항에는 이미지가 필요 없는 경로의 자동 승인도 기록돼 있다. 실제 프런트엔드는 별도 범위이며, 이 저장소의 API와 백엔드 구현만으로 전체 사용자 UI를 구현했다고 쓰지 않는다.

**의도적으로 나눈 범위**: SNS 게시와 광고 성과에 따른 학습은 후속/보류 범위다. 기초 모델의 우선순위는 요청→생성→검토 흐름이다. 요구사항에 들어 있는 최종 QC·자막/로고 합성 등이 모두 현재 완료됐다고 주장하지 않는다.

**실험과 피드백→변경의 근거**:

- 2026-09-17~18 기록: 텍스트·참조 이미지·오디오를 포함한 세 경로가 완성본 조립까지 관통했다. 품질은 미달이라고 명시돼 있다.
- 2026-10-01 기록: 수정 범위에 맞춰 나레이션을 바꾸거나 유지하는 두 경우를 실행했다. 바뀐 장면의 문장만 재합성하는 흐름이 기록돼 있다.
- 검토자가 수정 영상의 원치 않는 발화를 지적했다. 원인 조사에서 문맥용 영상에 섞인 TTS가 생성 모델의 발화를 유도하는 것으로 판단했고, 화면과 배경음만 문맥으로 넘기는 방식으로 바꿨다. 재실행에서 해당 교체 클립의 음성 활동 탐지 0건이 기록됐다. 이는 특정 실험의 관찰이며 전체 발화 오류를 해결했다는 뜻이 아니다.
- 별도의 인물 대사 실험은 시작 지연, 알아듣기 어려운 발화, 수정 범위 끝에서 문장 잘림을 보고한다. 이는 해당 실험 기록의 관찰이다. 2026-10-01 사용자 정정으로 현재는 레퍼런스로 연속성·목소리 일관성을 일정 수준 구현했고, 남은 과제는 모델별 생성 결과의 품질 차이임을 확인했다.

**바로 쓸 수 있는 방향**:

> 업무 담당자가 원하는 광고를 자연어로 설명하고 시나리오와 참조 이미지를 검토한 뒤 생성하는 흐름을 설계했습니다. 전체 재생성뿐 아니라 필요한 구간과 나레이션을 수정하는 경로도 구현했습니다. 실제 실험에서 검토자의 발화 오류 지적을 바탕으로 수정용 문맥의 오디오 구성을 바꿨으며, 최종 광고 품질과 제작 시간 절감은 추가 검증이 필요합니다.

**제외할 주장**: 제작 시간 절감률, 운영자 개입 감소, 실제 SNS 게시 성공, 광고 성과 개선, 고객이 사용하는 완성 서비스. 자료 없이 수치를 추가하지 않는다.

**2026-10-01 현재 상태 정정:** 사용자 설명이 현재 구현의 근거다. 기존 뮤직비디오·광고·드라마 실패나 별도 대사 실험의 한계를 현재 장편·목소리 기능 전체의 미해결로 쓰지 않는다. 레퍼런스 기능으로 연속성과 목소리 일관성을 일정 수준 구현했으며 남은 과제는 모델별 결과 품질. 레퍼런스 방식·모델 선택 판단·직접 기여·실제 사용 결과를 후속 질문했다.

## STF-01 — 인력 분석: 평균 대신 서비스 수준을 지키는 피크 계획

**확인 자료**: 2026-02-19 작성된 인력 보고서 8페이지를 렌더링해 직접 판독했다. 글자 추출로는 내용이 나오지 않았다. 원본과 페이지 이미지는 저장소에 추가하지 않았다.

**문제와 판단**: 시즌별 평균 수요만으로 채용하면 고부하일에 대응하지 못한다. 보고서는 최근 고부하일의 Q90을 피크 계획 기준으로 두고, 기존 인력의 처리량을 제외한 잔여 수요를 추가 인력으로 흡수하도록 산정한다. 하락 추세는 R²가 약 0.06으로 설명력이 낮아 참고값으로만 사용한다.

**우선순위와 trade-off**: 실패한 날의 높은 1인당 처리량을 안정 처리능력으로 사용하지 않는다. 서비스 수준 임계에 맞는 실무 처리량과 더 보수적인 처리량을 나눠 기본안과 +1명 완충안을 제시한다. 비용 최소화만을 목표로 하기보다 응답률 목표와 결근·숙련도 편차를 고려한다.

**보고서상 역검증**:

- 총호수 600건 이상인 88일을 대상으로 충분 64일·부족 24일을 구분했다.
- 선택한 균형 임계값의 정확도는 90.9%, 부족일 탐지는 23/24일(약 96%)로 보고됐다. 고부하 부분집합의 탐지도 별도로 기록한다.
- 운영 규칙은 시즌 시작 2주 전 인력 확보, 인당 부하가 임계값을 넘으면 증원 판단, 인상담률 90% 이상 유지다.

이는 보고서에 기록된 과거 데이터 역검증이며, 이번에 원 데이터로 재계산하거나 독립 표본에서 검증하지 않았다. 개별 직원 자료, 상세 일별 실적, 내부 인력표는 요약에서 제외했다.

**600만 원의 증거 경계**: 기존 포트폴리오는 2026년 여름 인건비 절감을 서술한다. 이 보고서는 그 이전인 2월의 계획·역검증 자료이며, 여름 적용 인원·급여·비교안·절감 산식·적용 후 서비스 수준을 증명하지 않는다. **2026-10-01 사용자 답변으로 적용 성과를 확인했다:** 전년 대비 실제 인력 3명을 줄여 600만 원을 절감했으며, 분석이 실제 인원 감소로 이어졌다. 보고서는 분석·역검증의 근거, 사용자 설명은 채용 반영·절감 성과의 근거로 구분한다. 상세 근무·급여 산식은 답변에 포함되지 않았다. 후속 답변에서 인력 조정 후 목표 소통률 90% 상회, 2026년 추석 계획보다 1명 부족한 운영에서 소통률 88~91%와 1명분 처리량 부족을 설명했다. 분석 계획과 실제 운영의 대조 사례로 기록한다.

**바로 쓸 수 있는 방향**:

> 시즌 채용을 평균 수요 대신 고부하일의 피크와 응답률 목표에 맞춰 설계했습니다. 설명력이 낮은 추세 예측을 주 기준에서 제외하고, 과거 부족일 탐지 결과와 보수적 완충안을 함께 제시해 채용·증원 운영 규칙으로 연결했습니다.

전년 대비 3명·600만 원 절감 성과를 공개 본문에 반영했다. 보고서 역검증과 사용자 설명의 적용 성과·운영 결과를 각각 연결한다. 추석의 88~91%를 일괄 목표 달성으로 바꾸지 않는다.

## RAG-01 — RAG: 실제 법령 실험과 별도 검증 Core의 경계

**확인 자료**: 통합 저장소 README, 별도 Core README·아키텍처, 2026-07-07 작업 로그의 live 관찰, 2026-07-08 thinking 비교, 2026-07-09 parser probe, 2026-07-30 두 소비자 smoke와 2026-08-04 분리 작업 기록. 모델·서비스를 다시 실행하지 않았다.

**역할**: 통합 프로젝트는 모호한 요청을 구조화하고 문서 검색·답변 후보·근거 검증으로 이어지는 흐름이다. 별도 Core는 호출 서비스의 후보를 검증해 결과를 반환하며, 최종 저장·채택·review 결정은 호출 서비스가 소유한다. 두 저장소를 별개 제품 성과로 중복 집계하지 않는다.

**기술 범위 이상의 관찰**:

- 실제 법령 질문에서 검색 범위를 제한하지 않으면 유사한 다른 법령 조항을 먼저 잡아 human review로 넘어간 기록이 있다. 질문 범위를 명확히 하는 이유를 보여주지만 사용자 시간 절감은 측정하지 않았다.
- 근거 부족을 정직하게 알리는 문장을 실체 주장으로 추출하는 문제가 발견됐다. 생성뿐 아니라 주장 추출 단계에서 불확실성 설명을 분리하도록 수정했고, 관련 live 재실행에서는 주장 0개·근거 링크 0개인 근거 부족 답변을 통과시켰다. ‘모름을 표현한 답변’의 통과이지 근거 있는 답변 정확도의 성공 표본이 아니다.
- thinking 비교는 동일한 단일 법령 질문과 제한된 검색 조건에서 수행했다. 두 모드가 후속 smoke를 통과했으나, thinking 모드의 앞선 실행은 구조 파싱에 실패했고 재실행이 통과했다. 토큰·지연 부담과 불안정성이 관찰됐지만 전체 평가셋의 품질 우열로 일반화하지 않는다.
- parser probe는 로컬 문서/fixture 167개 중 parsed 154, parser_error 2, unsupported 11을 기록한다. OCR·표 구조 등의 한계가 있다. 실제 고객 문서 전체의 처리 성공률로 바꾸지 않는다.
- 두 소비자 Core smoke는 준비 상태·인증 실패·모델 의존성 장애에서의 거절과 복구를 확인했다. 정상 HTTP 응답도 근거 collection이 비어 **reject**였다고 명시한다. 이를 코퍼스 기반 검증 성공으로 소개하지 않는다.

**바로 쓸 수 있는 방향**:

> 법령 검색에서 답변 후보와 근거를 구분하고, 부족하거나 확인할 수 없는 근거를 사람의 검토로 넘기는 검증 흐름을 실험했습니다. 실제 모델 실행에서 검색 범위 혼동과 ‘근거 부족 설명을 주장으로 추출’하는 실패를 발견해 수정했습니다. 검증 Core는 다른 서비스가 호출하는 기반으로 분리했으며, 실제 사용자의 답변 준비 시간과 정확도는 별도 검증이 필요합니다.

**제외할 주장**: 법률 답변 정확도 보장, human review 감소율, 실사용 완료율, parser 수치를 법률 답변 정확도로 사용, HTTP 200을 검증 승인으로 해석, 두 소비자를 실제 고객 두 곳으로 서술.
